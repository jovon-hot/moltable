# Pinecone 实战：给 Moltable 加一层托管向量检索

上一篇《[AI Agent Memory 全家桶](/blog/agent-memory-stack-comparison)》给了结论：**检索层与同步层是两个正交问题**——Pinecone 解决「大规模语义检索」，Moltable 解决「一个账号把检索背后这些记忆资产跨设备、跨 Agent 在线同步，换电脑/换框架不丢」。两者不冲突，反而该组合。这篇把「检索层」真正接进来，手把手给你的记忆资产加一层 Pinecone 托管向量检索，附可直接照抄的代码。

先说清楚一件事：**加 Pinecone 不是为了「替换」现有的 pgvector 存储，而是为了「分层」**。这决定了后面所有设计选择。

## 一、先想清楚：为什么是「分层」而不是「替换」

现在的语义检索链路是：**本地 embedding（MiniLM-L6-v2，384 维）+ pgvector（HNSW 余弦）**。这套在单机、中小规模下完全够用，零外部依赖。但到一定规模会出现三类典型瓶颈：

| 瓶颈 | pgvector 自托管的表现 |
|------|----------------------|
| HNSW 重建 | 批量写入后索引重建会短暂锁表，写入放大 |
| 并发检索 | 向量相似度在 PG 里是 CPU 密集操作，高并发下与业务查询抢资源 |
| 多租户过滤 | 每个查询都要 `WHERE user_id = ... AND soul_id = ...`，索引过滤效率随租户数下降 |

Pinecone 把这三件事做成了免运维 SaaS：serverless 弹性扩容、低延迟、SLA、内置 metadata 过滤和 namespace 隔离。

但 Pinecone 的边界也很诚实：**它能飞快地告诉你「哪条记忆最像这个问题」，却回答不了「这条记忆属于谁、此刻在哪个项目里」**——归属关系始终由主存储（Postgres）负责。所以正确的姿势是：

```
PostgreSQL + pgvector      ← 主存储：记忆 / 项目 / 关系的事实源（归属关系在这里）
Pinecone（托管向量云）      ← 检索层：大规模语义相似度，扛「海量 + 并发 + 免运维」
Moltable（Agent 在线同步层）  ← 同步层：把 SOUL / Skills / config.yaml / memories/ 打包成
                              版本化、去重的 bundle，换电脑/换框架一条 pull 还原
```

**事实源留在 Postgres，语义检索下沉到 Pinecone，整套调教成果交给 Moltable 在线同步。** 下面按这个架构动手。

## 二、四步接上 Pinecone

### Step 1：建 index（维度必须对齐 384）

embedding 服务输出 **384 维**（`all-MiniLM-L6-v2`，见 `server/services/embedding.py`）。Pinecone index 的维度必须和写入的向量维度一致，否则直接报错。用 cosine 度量，和 pgvector 的 `vector_cosine_ops` 保持一致：

```python
from pinecone import Pinecone, ServerlessSpec

pc = Pinecone(api_key="YOUR_PINECONE_API_KEY")

pc.create_index(
    name="moltable-memories",
    dimension=384,          # 与 embedding.py 的 _DIM 一致
    metric="cosine",        # 与 pgvector 的 cosine 一致
    spec=ServerlessSpec(cloud="aws", region="us-east-1"),
)
```

> ⚠️ **维度对齐是第一个坑**。很多人默认用 Pinecone 内置 embedding（1536 维）的 index，再用本地 MiniLM（384 维）写入，upsert 时报 dimension mismatch。要么统一用 384 本地模型，要么统一用 Pinecone 内置 `embed` 端点，别混。

### Step 2：写一个 PineconeAdapter，镜像 VectorStore 接口

`server/services/vector_store.py` 已经定义了一套清晰的接口：`insert / get / list / search / delete / stats`。我们写一个 `PineconeAdapter` 实现同样的方法签名，这样上层调用方几乎无感知地切换：

```python
# server/services/pinecone_adapter.py
from pinecone import Pinecone

class PineconeAdapter:
    """托管向量检索适配器 — 镜像 VectorStore 接口，可无感切换。"""

    def __init__(self, api_key: str, index_name: str = "moltable-memories"):
        self.index = Pinecone(api_key=api_key).Index(index_name)

    def insert(self, user_id: str, content: str, embedding: list[float],
               category: str = "fact", soul_id: str | None = None,
               memory_id: str | None = None, **meta) -> dict:
        mid = memory_id or f"{user_id}:{_short_uuid()}"
        vector = {
            "id": mid,
            "values": embedding,
            "metadata": {
                "user_id": user_id,
                "category": category,
                "soul_id": soul_id or "",
                "content": content[:2000],  # 只存前 2000 字符，正文回 PG 取
            },
        }
        self.index.upsert(
            vectors=[vector],
            namespace=user_id,  # 关键：按 user 做 namespace 硬隔离
        )
        return {"id": mid, "user_id": user_id, "content": content}

    def search(self, user_id: str, query_embedding: list[float],
               top_k: int = 5, threshold: float = 0.5,
               category: str | None = None,
               soul_id: str | None = None) -> list[dict]:
        filter_ = {"user_id": {"$eq": user_id}}
        if category:
            filter_["category"] = {"$eq": category}
        if soul_id:
            filter_["soul_id"] = {"$eq": soul_id}

        resp = self.index.query(
            vector=query_embedding,
            top_k=top_k,
            namespace=user_id,           # 与写入时同名，双重保险
            filter=filter_,
            include_metadata=True,
        )
        results = []
        for m in resp.get("matches", []):
            if m["score"] < threshold:
                continue
            results.append({
                "id": m["id"],
                "content": m["metadata"].get("content", ""),
                "similarity": round(m["score"], 4),
                "category": m["metadata"].get("category"),
                "soul_id": m["metadata"].get("soul_id"),
            })
        return results

    def delete(self, user_id: str, memory_id: str) -> bool:
        try:
            self.index.delete(ids=[memory_id], namespace=user_id)
            return True
        except Exception:
            return False
```

两个设计点值得展开：

1. **`namespace=user_id` 是硬隔离的第一道墙**。Pinecone 的 namespace 是物理隔离的向量子空间，query 时指定 namespace 就从根上杜绝了「查串租户」——比只靠 metadata filter 更稳。metadata 里再带一层 `user_id` 是双保险（防止 namespace 配置写错时静默串库）。

2. **`content` 只存前 2000 字符作为回显**，正文始终回 Postgres 取。向量库的 metadata 不该存大字段，既费钱又拖慢检索。这也是「检索（Pinecone）↔ 事实源（PG）」分层在实现上的体现：Pinecone 只负责「哪条最像」，PG 负责「这条的完整内容 + 归属关系」。

### Step 3：写入路径——memory 落库时同步 upsert

在记忆写入的 service 层加一个钩子，PG 写入成功后异步同步到 Pinecone（`soul_id` / `category` 一并带过去，供检索时过滤）：

```python
# 伪代码：在 memory 创建流程中追加
async def create_memory(user_id, content, category, soul_id):
    embedding = embed(content)                       # 384 维，本地 MiniLM
    memory = await pg_repo.insert(...)               # ① 事实源：写 PG（主存储）
    asyncio.create_task(
        pinecone_adapter.insert(                     # ② 检索层：异步同步 Pinecone
            user_id, content, embedding,
            category=category, soul_id=soul_id,
            memory_id=memory["id"],
        )
    )
    return memory
```

> 两个关键决策：**① PG 是唯一事实源**（pinecone 挂了不影响记忆可读，重建即可恢复）；**② 异步写**（Pinecone 的延迟不进主链路，检索层是缓存语义，不是主存储）。

### Step 4：检索路径——带 namespace + filter 查询

检索时从当前 Soul 上下文里带上 `soul_id` / `category`，让 Pinecone 的 filter 帮你在语义相似的候选里，再做一层「这是谁的、什么类型的」硬过滤：

```python
def recall(user_id, query, soul_id=None, category=None, top_k=5):
    q_emb = embed(query)
    hits = pinecone_adapter.search(
        user_id, q_emb, top_k=top_k,
        category=category, soul_id=soul_id,
    )
    # 回 PG 取完整正文 + 归属关系（belongs_to soul / project）
    return [enrich_from_pg(h["id"]) for h in hits]
```

这一步的价值在于：**Pinecone 的语义召回 + 主存储的归属过滤**，得到的不是「泛泛相关的知识片段」，而是「当前这个 Soul、这个项目语境下，最相关的记忆」。

## 三、隔离：四层边界

把前面的设计收拢成一个明确的分层模型：

| 层 | 用什么 | 隔离手段 | 负责什么 |
|----|--------|----------|----------|
| 主存储 | Postgres | RLS（`server/schema.sql` 已启用） | 谁的记忆、属于哪个 project、关系 |
| 检索 | Pinecone | namespace + metadata filter | 大规模语义相似度 |
| 嵌入 | 本地 MiniLM（384） | 模型一致 | 文本 → 向量 |
| 同步/备份 | Moltable | 每实例一个 Agent + CAS 去重 | 整套调教成果在线同步 + 文件级备份兜底 |

各层各司其职，任何一层替换或故障，其他层不受影响——这就是「分层」的意义。

## 四、什么时候该上 Pinecone（而不是继续 pgvector）

不是所有部署都要接 Pinecone。给一个诚实的判断标准：

- **向量 < 10 万、单机、低并发** → 继续用 pgvector，零成本零运维，别过度设计。
- **向量 10 万 ~ 100 万、检索 QPS 上升** → 先优化 pgvector（HNSW 参数、分区、只存 embedding 不存正文）。
- **向量 > 100 万、或要 SLA / 弹性扩容 / 免运维** → 上 Pinecone，按本文四步接。

一句话：**Pinecone 是 pgvector 的「生产升级路径」，不是它的替代品**。它接的是「检索」这一个环节；记忆资产的所有权永远在你自己手里——Moltable 负责把它们在线同步，文件级备份版本化存好，随时导出/删除，不用来训练。

## 总结

- Pinecone 解决「检索 / facts」，Moltable 解决「Agent 在线同步」，两者是分层不是二选一。
- 接 Pinecone 四个关键点：**维度对齐 384、namespace=user_id 硬隔离、metadata 带 soul/category 供过滤、PG 仍是唯一事实源**。
- 事实源留在 Postgres（RLS 隔离），语义检索下沉 Pinecone；调教成果（SOUL / Skills / config.yaml / memories/）交给 Moltable 在线同步，文件级备份兜底——**检索再快，丢了等于零**。
- 规模没到之前别急着上托管云——pgvector 在中小规模下依然是最优解。
