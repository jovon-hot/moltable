**我是一名独立开发者，一个人同时维护三个产品。2026 年，我的日常工作已经被 AI Agent 重度接管——但代价是，我变成了一个「跨 Agent 协调员」，每天花大量时间让不同的 AI 重新认识我。**

这篇文章不是产品广告，是一份真实的使用记录：我的工具链长什么样、卡在哪里、怎么解决的。如果你也是独立开发者或者小团队，大概率会看到自己的影子。

---

## 我的工具链：四个 Agent，一套流程

先交代清楚我在用什么。我不用一个「全能 Agent」干所有事，而是按任务类型分流：

- **Claude Code / OpenCode CLI**：写代码、review PR、跑测试。这是我最重度的场景，一天几十次调用。
- **Hermes Agent**：桌面 AI 助理，接管内容运营、定时任务、文档整理这类「例行但琐碎」的活。
- **Codex**：快速原型验证，一个想法想先跑通再投入。
- **本地知识库**：1100+ 节点的个人知识体系，从项目决策到领域认知都沉淀在这里。

这套组合拳的好处是**每个 Agent 都在它最擅长的场景里**。坏处也在这里——**它们彼此不认识，而且都不认识我**。

---

## 真正的瓶颈：不是模型，是身份

用了一个月之后，我发现最耗精力的不是写 prompt，而是**重复交代「我是谁」**。

举三个真实发生的例子：

1. **环境偏好反复丢失**。我的本地代理环境有个坑：跑 OpenCode 之前必须先 `unset` 掉代理环境变量，否则 npm registry 全部超时。这个坑我踩了一次，在 OpenCode 里修好了。第二天换 Claude Code，它又踩了一遍——因为它不知道我在 OpenCode 里已经总结过这条规则。

2. **项目约定互相矛盾**。技术栈统一是我的强迫症：要么全 MDX 要么全 TSX。但一个 Agent 记住的是「这个项目用 MDX」，另一个 Agent 记住的是旧版本「用 TSX」，于是同一个仓库里出现了两套写法。

3. **每次新会话都从零开始**。「你是谁、你偏好什么、这个项目的历史决策是什么」——这些问题，每个 Agent、每个新会话，都要重新回答一遍。

我算过一笔账：**这些「重新认识你」的成本，比模型调优的边际收益大得多**。模型从 v3 升到 v4 给我省 10 分钟，但身份失忆每天浪费我 1 小时。

---

## 解法：把「我是谁」从 Agent 里抽出来

问题的本质是：**身份和记忆被锁死在了单个 Agent 里**。Claude Code 记得的事，OpenCode 读不到；换个会话，连同一个 Agent 都忘了。

我给自己装了一层独立的 **Identity 层**——就是 Moltable（我自己在做的东西，这里正好 dogfooding）。核心逻辑不是「存更多对话记录」，而是把身份拆成三件可复用的东西：

- **Persona**：「我是一个什么样的开发者」——技术栈偏好、命名习惯、项目约定、沟通风格。
- **分类记忆**：按类型归档的事实——决策、偏好、模式、项目状态，而不是一条不分青红皂白的对话流水。
- **跨 Agent 同步**：上面这些东西通过标准协议（MCP / A2A）暴露给任何 Agent 读取，不再锁死在某个聊天窗口里。

关键区别在于：**向量数据库存的是「你说了什么」，身份层存的是「你是谁」**。前者是流水账，后者是结论。结论才能跨 Agent 复用。

## 一天的真实走查

写代码场景最能说明问题。我的一个典型上午：

1. 在 OpenCode 里开个新会话，它通过 Identity 层直接读到我的 Persona——知道我是谁、项目用什么技术栈、`unset` 代理这条环境坑已经写在记忆里，不用我再交代。
2. 写完代码，切到 Claude Code 做 review。它读的是**同一份**项目约定和决策历史，不会给我一套和 OpenCode 冲突的建议。
3. 中间有个想法要验证，扔给 Codex 做原型。它同样带着我的偏好和上下文开工，不是从白纸开始。
4. 晚上 Hermes 跑定时内容任务，它知道这个博客用什么格式、什么语调，产出直接能用。

全程我没有重复交代过一次「我是谁」。

## 诚实复盘：有效的地方，和还没做好的地方

我不想把这事讲成银弹。真实情况是：

**有效的地方：**
- 跨 Agent 偏好同步，立竿见影。环境坑、命名习惯、项目约定，说一遍就到处生效。
- 决策历史可追溯。三个月前「为什么这个项目从 TSX 迁到 MDX」的上下文还在，新 Agent 接手不会翻车。

**还没做好的地方：**
- **身份与记忆的边界还不清晰**。哪些算「长期身份」、哪些算「临时上下文」，自动分类还不够准，偶尔要手动整理。
- **多 Agent 并发写同一份记忆时的冲突**，还在靠人肉协调。
- **可信度问题**：一个 Agent 写进去的记忆，另一个 Agent 凭什么信？这需要验证机制，而不是盲目信任。

最后一点尤其重要——**灵魂资产备份的前提是信任**。如果每个 Agent 都往备份仓库乱写，这层基础设施会迅速变成垃圾场。这也是我下一步要做的事。

---

## 给独立开发者的三条建议

1. **先治理身份，再堆模型**。多 Agent 是趋势，但如果没有统一的身份层，Agent 越多，协调成本越高，边际收益可能为负。
2. **存结论，别存流水**。「用户喜欢 TypeScript」是结论，「用户 3 月 5 日说了一句 TypeScript 相关的话」是流水。只有结论能跨会话、跨 Agent 复用。
3. **给记忆加验证**。让 Agent 能互相查证、纠错，而不是无条件采信。信任是身份基础设施的地基。
