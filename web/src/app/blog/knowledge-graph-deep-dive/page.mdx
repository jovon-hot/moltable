## 为什么 AI Agent 需要知识图谱？

向量搜索很好，但它有个致命缺陷：**它不理解关系**。

当你问「我用什么工具管理 Kubernetes 集群？」时，向量搜索能找到包含「Kubernetes」和「工具」的文档片段，但它不知道：
- Kubernetes 是你正在运维的系统（工具）
- Helm 是你用来部署的工具（用途）
- 你的团队使用 Terraform 管理基础设施（工具链）

这就是知识图谱的用武之地。它不是替代向量搜索，而是**补充**它——用结构化的实体关系回答「谁、用什么、做什么」这类问题。

## 设计哲学：为什么自己写，不用图数据库？

市面上有很多成熟的图数据库——Neo4j、Neptune、ArangoDB、Dgraph。但 Moltable 的知识图谱服务选择了一条不同的路：

| 维度 | 图数据库 (Neo4j) | Moltable 知识图谱 |
|------|-----------------|------------------|
| 依赖 | JDK, Cypher, 专用驱动 | Python stdlib only |
| 部署 | 独立服务 + 内存管理 | 嵌入在同进程中 |
| 数据量级 | 十亿节点 | 每用户数千节点 |
| 查询语言 | Cypher / Gremlin | Python dict + 集合运算 |
| 学习成本 | 需要学习图查询语言 | 标准 Python 操作 |
| Agent 场景 | 过度工程化 | 恰到好处 |

**核心判断**：AI Agent 的知识图谱不是要处理十亿节点的社交网络，而是要为单个用户建模几百到几千个实体和关系。在这个规模下，in-process 的方案比 client-server 快一个数量级，也简单一个数量级。

### 7. 人名（正则匹配）

人名是最难用关键词匹配的，所以使用正则：

```python
# 匹配中文姓名（2-4 个字）
CN_NAME_RE = re.compile(r'(?:王|李|张|刘|陈|杨|赵|黄|周|吴|...)[\u4e00-\u9fff]{1,3}')
# 匹配英文首字母大写组合
EN_NAME_RE = re.compile(r'\b[A-Z][a-z]+ [A-Z][a-z]+\b')
```

### 匹配策略

不是简单 `if word in text`。系统使用了一套层级匹配策略：

1. **精确匹配**：全词匹配（\b 边界），防止「Go」匹配到「Google」
2. **小写匹配**：将文本转为小写后匹配（处理大小写变体）
3. **Case-Sensitive 回退**：对小写会误匹配的词，在原文中精确匹配
4. **正则匹配**：用于人名、电子邮件等结构化实体

```python
def _find_entities(self, text: str) -> list[tuple[str, str, int, int]]:
    entities = []
    text_lower = text.lower()
    
    # 1. 小写关键词匹配
    for kw, display in LANGUAGES.items():
        for m in _word_boundary_re(kw).finditer(text_lower):
            entities.append((LANGUAGE, display, m.start(), m.end()))
    
    # 2. Case-sensitive 回退
    for kw, display in LANGUAGES_CASE_SENSITIVE.items():
        for m in re.finditer(r'\b' + re.escape(kw) + r'\b', text):
            entities.append((LANGUAGE, display, m.start(), m.end()))
    
    # 3. 人名正则（中英）
    for m in CN_NAME_RE.finditer(text):
        entities.append((PERSON, m.group(), m.start(), m.end()))
    
    # ... 对 TOOLS, ORGS, PROJECTS, CONCEPTS, LOCATIONS 重复
    return entities
```

## 第二层：关系构建 — 从共现到结构化知识

有了实体，下一步是找出它们之间的关系。Moltable 使用两种互补的策略：

### 策略 A：共现边（Co-occurrence Edges）

最朴素但最有效的方法：如果两个实体经常在同一条记忆中同时出现，它们就有关系。

```python
def _build_cooccurrence_edges(self, memories: list) -> list[dict]:
    """为每对在 N 条记忆中同时出现的实体创建边"""
    cooccur = defaultdict(lambda: defaultdict(int))
    
    for mem in memories:
        entities = self._find_entities(mem["content"])
        entity_names = list({e[1] for e in entities})  # 去重
        
        for i in range(len(entity_names)):
            for j in range(i + 1, len(entity_names)):
                cooccur[entity_names[i]][entity_names[j]] += 1
                cooccur[entity_names[j]][entity_names[i]] += 1
    
    # 仅保留出现 ≥ 2 次的边（过滤噪声）
    edges = []
    for a, neighbors in cooccur.items():
        for b, weight in neighbors.items():
            if weight >= 2:
                edges.append({
                    "source": a, "target": b,
                    "type": "co_occurrence",
                    "weight": weight,
                    "id": f"{a}--{b}--cooccur"
                })
    return edges
```

为什么阈值设为 2？因为单次共现可能是巧合（「我今天用 Python 写了脚本，然后去吃了 Python 牌的巧克力」）。两次以上共现才说明有真实关联。

### 策略 B：模式匹配边（Pattern Edges）

共现能告诉我们「A 和 B 有关」，但不能告诉我们是什么关系。模式匹配弥补了这一点：

```python
RELATION_PATTERNS = [
    # (pattern, source_type, relation, target_type)
    (r"(\w+) works? (?:at|for|with) (\w+)", PERSON, "works_at", ORG),
    (r"(?:use|using|with|via) (\w+)", None, "uses", TOOL),
    (r"built (?:with|using) (\w+)", PROJECT, "built_with", TOOL),
    (r"deploy(?:ed|s)? (?:to|on|with) (\w+)", PROJECT, "deploys_to", TOOL),
    (r"(?:learn|learning|studying) (\w+)", PERSON, "learning", LANGUAGE),
    (r"(?:found|founded|created|built) (\w+)", PERSON, "created", PROJECT),
    # ... more patterns
]
```

每个模式有三个要素：触发词、主语（可选）、宾语。当一条记忆同时包含实体和这些动词模式时，系统推断出有向关系。

## 性能：零依赖的代价和收益

### 时间复杂度

| 操作 | 复杂度 | 实测 (10K 记忆) |
|------|--------|----------------|
| 实体提取 | O(n·k) k=关键词数 | ~0.5ms/条 |
| 共现建边 | O(m²) m=实体数 | ~3ms/条 |
| 邻居查询 | O(e) e=边数 | `小于1ms` |
| BFS 路径 | O(v+e) | `小于5ms` |

### 内存占用

- 关键词词典：~50KB（所有词表在模块加载时一次性构建）
- 每用户图谱：~100KB-500KB（100-1000 实体 + 边的 dict）

### 为什么不用 LLM？

很多人问：为什么不直接用 LLM 做实体识别和关系提取？

答案很简单：**成本**。对于 Agent 的日常记忆流（每天几十到几百条），如果用 LLM 逐条做 NER + RE，成本是：

- GPT-4o-mini: ~$0.15/1K tokens × 平均 500 tokens/条 = $0.075/条
- 每天 100 条记忆 = $7.5/天 = $225/月

而关键词匹配：**零成本，零延迟，始终在线**。

当然，LLM 的优势是覆盖面更广——它可以识别出词典中没有的实体。最佳实践是**混合方案**：关键词匹配处理已知实体，LLM 周期性扫描发现新实体，然后自动加入词典。

## 未来方向

当前的知识图谱服务已经是 AI Agent 的可靠基础设施，但还有几个激动人心的方向：

1. **增量 LLM 实体发现**：周期性用 LLM 扫描记忆，发现词典外的实体，自动扩充词表
2. **时序衰减**：旧关系权重随时间衰减，避免过期信息污染图谱
3. **跨用户知识融合**：在团队场景下，识别不同成员图谱中的共同实体和互补知识
4. **Graph RAG**：将图谱作为 RAG 的检索增强——把「相关记忆」拓展为「相关记忆 + 关联实体 + 知识路径」
5. **可视化导出**：生成 Mermaid/Graphviz 格式的图谱可视化

## 总结

Moltable 的知识图谱服务证明了一件事：**在 AI Agent 的场景下，「够用」比「强大」更重要**。

不需要 Neo4j 的分布式图计算引擎，不需要 Cypher 查询语言的学习曲线，不需要为每个实体识别调用 LLM。1200 行 Python、一套精心维护的关键词词典、两个简单的算法（共现 + 模式匹配），就能让 AI Agent 真正「理解」你的技术世界。

这是 Moltable 灵魂资产备份的关键拼图——Memory 告诉 Agent 你说过什么，Knowledge Graph 告诉 Agent 这些信息**如何关联**。
