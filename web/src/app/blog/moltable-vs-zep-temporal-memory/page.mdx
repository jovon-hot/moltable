## Why temporal memory became the battleground

A vector database answers "what do I know about this user?" A temporal memory system answers a harder question: **"how did what I know change, and why?"**

Consider a preference memory: `"preferred_language: Python"`. Stored once, it's a fact. But users change. The developer who preferred Python in January, Go in March, and Rust by June isn't just a set of stale snapshots — they're a *trajectory*. Agents that ignore the trajectory make the same mistakes humans make with a bad roommate: they assume today's state is the only state that ever existed.

Both Zep and Moltable recognize this. Their approaches, however, diverge sharply.

## Round 1: Temporal memory capabilities

### Zep's temporal knowledge graph

Zep's core insight: memory isn't just embeddings, it's *entities and their relationships over time*. Its temporal knowledge graph stores facts as graph nodes/edges with time-bounded validity — you can query "what did we believe about this entity last quarter?" and watch relationships evolve. It's genuinely good technology, backed by SOC 2 and HIPAA compliance, and it's why regulated industries (healthcare, finance) pay for it.

But there are three gaps:

1. **It's memory-only.** Zep tracks facts inside its graph, full stop — no sync, no snapshots, no rollback, no way to restore the agent itself if your laptop dies.
2. **It's closed SaaS.** No self-hosting, no MIT license, no way to own the substrate.
3. **Benchmarks aren't reproducible.** Zep claims SOTA results but has not published reproducible comparison numbers — a meaningful red flag when you're choosing infrastructure.

### Moltable's answer: sync the whole agent, not just its facts

Moltable is not a clone of Zep — it's a different bet on where agent infrastructure is heading. Instead of extracting facts from conversation, Moltable keeps **everything you taught the agent** in sync across your devices; `moltable backup push` takes file-level snapshots as the fallback:

- `SOUL.md` — character and behavioral principles
- `AGENTS.md` / `USER.md` — project and user context
- `config.yaml` — MCP configuration, secrets redacted
- `memories/` and `skills/` — memory and skill assets

Conversation logs (`state.db`/WAL/FTS) and secrets (`.env`/`*.key`) are automatically excluded — you sync *tuning work*, not raw logs.

The storage model is built for versioning:

1. **Bundle + manifest.** Each push produces a snapshot with a manifest describing exactly what changed.
2. **Content-addressed dedup (CAS).** Files are addressed by sha256, so unchanged content is never stored twice — the second push of a 200MB soul costs kilobytes.
3. **Per-Agent file-level version library.** Every framework instance (Hermes, OpenClaw, Claude, Codex) is its own sync unit (Agent) with an independent version library — snapshot, version number, rollback.
4. **Reference sync.** `moltable add-ref <name> <path>` folds an external knowledge base into the same sync, versioned alongside your soul.

Why does this matter for *temporal* concerns? Because "how did my agent change?" is a special case of "what did my agent look like at any point in time?" A knowledge graph can tell you how a fact evolved; a synced soul's snapshot can restore **the whole agent as it was** on any date — including the facts, the skills, the MCP wiring, and the memories that went with them.

**Verdict — Round 1: depends on the question.** If you need "how did this fact evolve, with enterprise compliance," Zep's graph is deeper. If you need "show me my agent as it was on any date — and restore it," Moltable — with versioned snapshots on top of continuous sync — is the only one of the two that can.

## Round 2: The sync layer — Moltable's unique advantage

This is the round Zep can't compete in, because **Zep doesn't have a sync story to compete with.**

Moltable's positioning puts it plainly: online sync, file-level backup (version management), incremental dedup, and reference sync — four capabilities in one platform. Zep ships exactly one of those four (temporal tracking).

### What "sync + backup" means in practice

- **MCP sync interface**: `search_memory` / `save_memory` let agents read and write your memory in real time; `auto_provision` restores your full context on a new device with one call.
- **Online sync + file-level backup**: your SOUL.md, AGENTS.md, USER.md, config.yaml (MCP, secrets redacted), memories/, skills/ follow your account across devices and agents; `moltable backup push` bundles them into versioned snapshots in object storage with content-addressed (CAS) dedup. Conversation logs and keys never included.
- **Version management**: every Agent keeps its own file-level version library — snapshot + version number, roll back to any past state. Zep's graph accumulates; Moltable's snapshots *version*.
- **Reference sync**: `moltable add-ref <name> <path>` folds external knowledge bases into the same sync, so your team's docs and your agent's soul travel together.

Zep answers the question "how do facts change?" Moltable answers "**how does everything you built change — and can you get it back?**" The second question is strictly more useful when your agent is the result of months of tuning.

## Round 5: Use case recommendations

**Choose Zep when:**
- You're a regulated enterprise (healthcare, finance) that *needs* SOC 2/HIPAA attestation out of the box
- You have a dedicated platform team and a six-figure infrastructure budget
- Your memory workload is dominated by entity-relationship queries across large corpora
- You're fine being locked into a vendor's graph format

**Choose Moltable when:**
- You run multiple agents (Hermes + Claude + Codex + OpenClaw) and want every instance's soul in sync — with file-level backup as insurance
- You've spent weeks tuning SOUL, skills, and MCP config — and refuse to lose that to a laptop change or a bad experiment
- You want versioning and rollback, not just facts: "show me my agent as it was last Tuesday"
- You want external knowledge bases folded into the same sync (`add-ref`)
- You want to own your data — export/delete anytime, never used for training
- You're a developer, startup, or mid-market team that refuses to pay $125+/mo for memory

**The honest truth**: if you're building agent infrastructure for a Fortune 500 hospital system, Zep's compliance story is real and valuable. If you're building agents for *people* — developers, creators, teams — the sync-first approach wins, because the thing people actually lose is not a fact graph; it's months of tuning.
