## Why temporal memory became the battleground

A vector database answers "what do I know about this user?" A temporal memory system answers a harder question: **"how did what I know change, and why?"**

Consider a preference memory: `"preferred_language: Python"`. Stored once, it's a fact. But users change. The developer who preferred Python in January, Go in March, and Rust by June isn't just a set of stale snapshots — they're a *trajectory*. Agents that ignore the trajectory make the same mistakes humans make with a bad roommate: they assume today's state is the only state that ever existed.

Both Zep and Moltable recognize this. Their approaches, however, diverge sharply.

## Round 1: Temporal memory capabilities

### Zep's temporal knowledge graph

Zep's core insight: memory isn't just embeddings, it's *entities and their relationships over time*. Its temporal knowledge graph stores facts as graph nodes/edges with time-bounded validity — you can query "what did we believe about this entity last quarter?" and watch relationships evolve. It's genuinely good technology, backed by SOC 2 and HIPAA compliance, and it's why regulated industries (healthcare, finance) pay for it.

But there are three gaps:

1. **It's memory-only.** Zep tracks facts inside its graph, full stop. It has no identity layer, no persona scoping, no cross-agent sync.
2. **It's closed SaaS.** No self-hosting, no MIT license, no way to own the substrate.
3. **Benchmarks aren't reproducible.** Zep claims SOTA results but has not published reproducible comparison numbers — a meaningful red flag when you're choosing infrastructure.

### Moltable's Temporal Memory Timeline

Shipped on August 6, 2026, Moltable's Temporal Memory Timeline is a direct, deliberate answer to Zep's temporal knowledge graph — built with a fundamentally different philosophy: **heuristics over LLM inference, identity-first data modeling, and zero new dependencies.**

The core service, `services/temporal_tracker.py` (524 lines), does three things:

**1. Automatic change detection — no LLM required.** Every time a memory is saved, the pipeline runs `detect_and_record_changes()` against the existing memory store. It watches for change markers — `"switched to"`, `"now using"`, `"no longer using"`, `"upgraded to"`, `"migrated to"`, and a dozen more — then extracts the affected entity (language, framework, editor, role, project, and Chinese equivalents like 语言/框架/工具/项目), looks up the current known value, and records a `FactTransition` with a confidence score.

```python
# Simplified from services/temporal_tracker.py
markers = ["switched to", "changed to", "now using",
           "no longer using", "upgraded to", "migrated to", ...]
for marker, change_type in markers:
    if marker in content.lower():
        entity = extract_entity(before_context)
        record_transition(user_id, entity,
                          old_value=lookup_current(entity),
                          new_value=after_context)
```

Because detection is pure string heuristics, there's **zero per-memory LLM cost** — important when you're processing thousands of memories. (It also works offline: the tracker falls back to an in-memory store when Supabase isn't available, which is how the 17 new tests in `test_temporal_tracker.py` run hermetically.)

**2. Pattern recognition.** Zep shows you a graph; Moltable *interprets* it. The tracker classifies each entity's transition history into four patterns:

| Pattern | Detection heuristic | What it tells you |
|---|---|---|
| **Oscillation** (震荡) | Flip-flopping between two values, ≥3 changes, near-total alternation | The user is undecided — surface *both* options, don't commit |
| **Gradual shift** (渐进迁移) | ≥3 changes, last two values equal but different from the first | A real migration in progress — commit to the new value, keep history |
| **Rapid change** (快速变化) | ≥3 changes with >0.5 changes/day | Something external changed (job, team, tooling) — re-onboard, don't assume |
| **Abandonment** | Change markers like "no longer using" | A fact died — stop recommending it entirely |

That oscillation detector is worth calling out specifically. An agent that knows a user flip-flopped between two editors three times in a week behaves differently from one that only knows the latest value — it stops nagging and starts offering *comparisons* instead. That's the difference between memory and understanding.

**3. Six query endpoints.** The `routes/temporal.py` router exposes the full timeline capability as a first-class API:

| Endpoint | Method | Purpose |
|---|---|---|
| `/api/temporal/timeline/{entity}` | GET | Full fact-change history for one entity, with confidence and persona tags |
| `/api/temporal/timelines` | GET | All tracked timelines, sorted by volatility (most-changed first) |
| `/api/temporal/state` | GET | Snapshot of *current* identity state — "who am I right now?" |
| `/api/temporal/changes` | GET | Recent-changes activity feed (7/30/90-day windows) |
| `/api/temporal/transitions` | POST | Manually record a transition (explicit preference updates) |
| `/api/temporal/report` | GET | Aggregate analysis: timelines + detected patterns + recent activity |

The `/state` endpoint is the quiet killer feature: a canonical, queryable "who is this user *today*" that any agent can pull before a conversation — powered entirely by the transition history.

**4. Persona-aware by design.** Every transition carries a `persona_id`. The same user can have different trajectories in their "Developer" persona vs. their "Architect" persona, and transitions are isolated per persona. **Zep has no persona concept at all** — it models one undifferentiated user.

**Verdict — Round 1: Moltable.** Zep's graph is deeper on *relationships between entities*; Moltable is sharper on *change over time*, cheaper to run, persona-scoped, and self-hostable.

## Round 2: The identity layer — Moltable's unique advantage

This is the round Zep can't compete in, because **Zep doesn't have an identity layer to compete with.**

The CHANGELOG entry for the temporal feature says it plainly: *"Moltable 独有优势：temporal + identity sync + memory health + persona — 四合一"* — temporal tracking, identity sync, memory health, and persona in **one platform**. Zep ships exactly one of those four (temporal).

### What "identity" means in practice

- **Identity Sync**: Moltable's three-layer architecture — Identity Layer (cross-platform unique ID) → Persona Layer (role management) → Sync Layer (one sync code restores everything). Your temporal memory follows you across Claude, Cursor, Codex, Hermes, OpenCode — not because you copied a database, but because your *identity* is the primary key.
- **Memory Health**: Moltable's `memory_health.py` scores every memory for staleness (90-day decay), contradiction, duplication (0.85 cosine threshold), and completeness — and auto-archives low-quality memories. Zep's graph accumulates; Moltable's memory *heals*. The temporal tracker and the health scorer work together: contradiction detection feeds the transition pipeline, and staleness scoring tells you which timeline entries are probably obsolete.
- **Persona**: one identity, many minds. Temporal transitions are scoped per persona, so a user's professional trajectory never pollutes their personal one.

Zep answers the question "how do facts change?" Moltable answers "**how does an identity change — and what stays the same?**" The second question is strictly more useful for building agents that feel like they *know you*.

## Round 5: Use case recommendations

**Choose Zep when:**
- You're a regulated enterprise (healthcare, finance) that *needs* SOC 2/HIPAA attestation out of the box
- You have a dedicated platform team and a six-figure infrastructure budget
- Your memory workload is dominated by entity-relationship queries across large corpora
- You're fine being locked into a vendor's graph format

**Choose Moltable when:**
- You run multiple agents (Claude + Cursor + Codex + Hermes) and want **one identity** across all of them
- You care about *how preferences change* — oscillation, gradual shifts, rapid churn — not just what they are
- You want memory that self-heals (staleness, contradiction, dedup) instead of accumulating rot
- You want personas: the same user, different trajectories, isolated timelines
- You want to own your data — MIT license, self-host, RLS-protected tables
- You're a developer, startup, or mid-market team that refuses to pay $125+/mo for memory

**The honest truth**: if you're building agent infrastructure for a Fortune 500 hospital system, Zep's compliance story is real and valuable. If you're building agents for *people* — developers, creators, teams — the identity-first approach wins, because people have identities, not just fact graphs.
