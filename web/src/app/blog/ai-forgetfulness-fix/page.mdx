情景你肯定不陌生：昨天花了半小时跟 Claude 调好了一个 Python 脚本的错误处理风格，今天打开新会话，它又用回默认风格了。你叹了口气，重新解释了一遍你的偏好——"用 try/except 包裹，错误信息用中文，日志级别用 WARNING"。

这就是 AI「失忆」——Agent 在跨会话中无法保持用户偏好。本文剖析五个根因，并给出一个即插即用的方案：把调教成果备份成版本化的灵魂资产，换机、换框架都不丢。

## 五大根因

### 1. LLM 天生无状态

这是一个设计选择，不是 bug。GPT、Claude、DeepSeek 都是无状态的——每次 API 调用都是一个独立的推理任务。模型的权重是固定的，它不"记得"任何历史。上下文窗口内的内容只是被编码为 token 输入，窗口一关闭，一切归零。

### 2. 会话上下文隔离

Claude Desktop 和 ChatGPT 的每个会话是独立沙箱。你可以在一个会话里教会 Agent 你的偏好，但这些偏好存储在客户端的对话历史中，不会传递到新会话。即使同一个平台，不同会话之间的 Agent 也是"陌生人"。

### 3. 调教成果没有版本管理

这是最根本的问题。你调教出来的 SOUL、自定义 skills、MCP 配置，散落在 Claude、Hermes、Codex 各自的目录里——没有版本号，没有备份，没有回滚。一次手滑覆盖 system prompt、一次升级冲掉配置、一次重装系统，几个月的心血直接清零。代码你有 Git，Agent 调教成果却连一个 `git init` 都没有。

### 4. 跨平台的碎片化

即使某个平台有记忆功能（如 ChatGPT 的 Memory），它也只存在于那个平台。你在 ChatGPT 里调教出来的东西，Claude 永远用不上。你给 Claude 调试好的 MCP 配置，Cursor 的 Agent 对此一无所知。每个工具各存一份，互不相通。

### 5. 没有一条命令的还原路径

即使你把配置文件备份到了网盘，还原依然是噩梦：新机器上要逐个重装 CLI、重放 MCP JSON、重建目录结构、回忆每个配置该放哪。备份是散装的，还原是手动的。而一个好工具应该像 `git clone` 一样：一条命令，完整还原。

五个根因，指向同一个结论：**AI 失忆是架构现实，治不好；但你的调教成果可以不上保险。**

## 修复方案：三步，给灵魂资产上保险

Moltable 不做记忆层——它不运行你的 Agent，只备份你的调教成果。一条命令把 SOUL、Skills、MCP 配置、记忆打包成版本化、去重的备份，换框架、换电脑都不丢。Tagline：**换 Agent，不换灵魂。**

### 第一步：安装并初始化

```bash
{`# 一条命令安装 Moltable CLI
curl -sL https://moltable.ai/install.sh | bash

# 生成备份配置，声明要备份的 Agent 实例
# （Hermes、OpenClaw、Claude、Codex，每实例一个备份源）
moltable backup init`}
```

### 第二步：打包上传你的灵魂资产

```bash
{`# 把 SOUL.md、AGENTS.md、USER.md、config.yaml、
# memories/、skills/ 打包成版本化备份并上传
moltable backup push

# 查看备份源与历史版本
moltable backup sources

# 把外部知识库一并纳入备份
moltable add-ref my-wiki ~/wiki`}
```

`config.yaml` 里的 MCP 配置会自动脱敏密钥；对话流水账（`state.db` / WAL / FTS）和 `.env`、`*.key` 会被自动排除——**备份的是资产，不是日志，更不是裸奔的密钥。**

### 第三步：需要时一条命令还原

```bash
{`# 换电脑 / 换框架：下载并还原
moltable backup pull

# 调坏了？回滚到上一版本
# （每个备份源独立版本库：快照 + 版本号 + 回滚）`}
```

关键原则：**每次把 Agent 调教到一个满意状态就 push 一次，打一个新版本。** 调坏了、覆盖错了，回滚即可——不要等换机那天才想起备份。

## MCP 接入：HTTP MCP，一行配置

Moltable 提供 HTTP MCP 服务（`https://api.moltable.ai/mcp`，`X-API-Key` 请求头鉴权，不是 npx/stdio 拉起），在 Hermes 或 Claude 中配置：

```json
{`{
  "mcpServers": {
    "moltable": {
      "type": "http",
      "url": "https://api.moltable.ai/mcp",
      "headers": {
        "X-API-Key": "molt_your_key_here"
      }
    }
  }
}`}
```

配置好后，Agent 可以通过 MCP 触发备份、查询备份源与版本；日常操作还是以 CLI 为主。**MCP 是 Moltable 的接入方式，不是给 Agent 喂记忆的通道。**

## 对比：修复前 vs 修复后

- **修复前**：新会话 → Agent 从头开始 → 你重复偏好 → 浪费 5-10 分钟；换机 → 手动重配 40-60 分钟；调坏 → 凭记忆重做
- **修复后**：调教成果每次 push 成新版本 → 换机 / 换框架一条命令 pull 还原 → 调坏一条命令回滚 → 零丢失

一个真实案例：FOST 集团的 CEO 每天用 Agent 处理 10+ 个任务，过去最怕的就是换电脑和调坏配置——重新调教一次至少半天。接入 Moltable 后，所有 Agent 实例都有了版本化备份，换机恢复从半天变成一条命令，调坏配置直接回滚到上一个可用版本。

## 进阶技巧

- **add-ref 引用外部知识库**：`moltable add-ref <名> <路径>`，把团队的内部 wiki、文档库一并纳入备份，知识库和灵魂资产一起管。
- **重要改动前先 push**：改 SOUL 或大规模调整配置前，先 push 一个版本——改坏了随时回滚，比任何后悔药都管用。
- **多实例分源管理**：Hermes、OpenClaw、Claude、Codex 每个实例一个备份源，独立版本库，互不干扰。
- **定期审查备份内容**：`moltable backup sources` 看看每个源的最新版本；密钥脱敏是自动的，但 add-ref 引用的路径记得定期清理。
