# 跨框架迁移复盘：把 168 个 Agent 从 OpenClaw 搬到 Hermes，我踩的 7 个坑

> **English summary**: I moved a personal AI setup from OpenClaw to Hermes — 168 agent roles, 188 skills, two local databases. The naive approach ("tar the whole directory and restore it on the other side") failed for seven distinct reasons, and the root cause was the same every time: I was treating *files* as the unit of migration when the thing that actually needed to move was an *account*. Real numbers, real pitfalls, and the file-vs-account mental model that finally worked.

我用了大半年的 AI Agent 环境，是 OpenClaw。后来主力换成了 Hermes。两边我都在跑。

所以我做了一件几乎所有换过 Agent 框架的人都做过的事：**把 `~/.openclaw` 整个打包，拷到新框架那边。**

结果：**几乎全废。**

不是拷丢了，是拷过去的东西根本「不认」。这篇文章把这次迁移复盘一遍——真实的目录结构、真实的体积、真实的报错，以及最后为什么我认定「跨框架迁移」这件事的原子单位不该是文件。

---

## 零、先把两边的底牌亮出来

迁移之前，我先数了一遍自己有什么。这步非常关键，因为**大部分人对「自己的 AI 资产到底在哪」的认知是错的**。

| 维度 | OpenClaw（源） | Hermes（目标） |
|------|---------------|---------------|
| 人格/灵魂文件 | `agents/*/` 下 **168 个角色目录**，每个含 `SOUL.md` + `IDENTITY.md` + `AGENTS.md` + `USER.md` + `HEARTBEAT.md` | `~/.hermes/` 下 `SOUL.md` + `USER.md` + `AGENTS.md`，**1 人 = 1 个总控灵魂** |
| 技能 | `skills/`（少量本地技能，大部分能力靠 agents 目录承载） | `~/.hermes/skills/` 下 **188 个 `SKILL.md`** |
| 长期记忆 | `memory/main.sqlite`（**sqlite 二进制**） | `memories/MEMORY.md` + `USER.md`（**纯 markdown**） |
| 配置 | `openclaw.json`（**46KB** 单文件 + 5 个 `.bak`） | `config.yaml` + `.env` |
| 定时任务 | `cron/jobs.json` | `cron/jobs.json`（同名，格式不同） |
| 本地数据库 | `memory/main.sqlite` 471KB + `memos.db` **137MB** | `state.db` **1.2GB**（9.3 万条 messages + 双套 FTS 索引） |

看到这张表，坑已经埋好了：**两边的「灵魂文件」根本不是同一种东西。**

---

## 一、坑 1：把「角色目录」当成「灵魂」

OpenClaw 的目录结构是这样的：

```
~/.openclaw/agents/
├── backend-architect/     SOUL.md  IDENTITY.md  AGENTS.md  USER.md  HEARTBEAT.md
├── anthropologist/        SOUL.md  IDENTITY.md  AGENTS.md  USER.md  HEARTBEAT.md
├── api-tester/            SOUL.md  IDENTITY.md  ...
└── ...（共 168 个）
```

Hermes 那边呢？

```
~/.hermes/
├── SOUL.md        ← 一个
├── USER.md        ← 一个
└── AGENTS.md      ← 一个
```

**粒度对不上。** OpenClaw 是「1 个人 = 168 个角色化身」，Hermes 是「1 个人 = 1 个总控灵魂 + 188 个技能」。

我一开始想的是「把 168 个 SOUL.md 合并成一个」。写了个脚本，把 168 份 markdown 拼在一起——**出来的是一个 40 万字的怪物**，模型读都读不完，注意力被稀释得干干净净，实际效果比原来任何一个角色都差。

### 教训

> **灵魂不是「一份文件」，是「一份被使用中的上下文」。** 迁移的时候你搬的不是字节，是「这个角色在什么场景下被激活」。粒度模型不兼容，硬合并只会得到一坨更差的东西。

正确做法是先做一次**语义映射**：168 个角色里，哪几个是你真的每天在用的？我盘下来只有 6 个。剩下 162 个是「收藏」不是「资产」。**迁移的第一步是删，不是搬。**

## 二、坑 2：把 1.2GB 当宝贝搬

这点最反直觉，也最值得写。

我第一次迁移时，为了「数据零丢失」，把两个框架的本地数据库全拷了。总共有：

- `memos.db` — **137MB**
- `state.db` — **1.2GB**
- `memory/main.sqlite` — **471KB**

搬完我心满意足。直到我发现问题：**新环境启动变慢了，但我的 AI 完全没有变聪明。**

拆开看才明白：

| 数据库 | 体积 | 性质 | 该不该同步 |
|--------|------|------|-----------|
| `state.db` | 1.2GB | 对话流水账（9.3 万条 messages + 双套 FTS 索引） | ❌ 排除 |
| `memos.db` | 137MB | memo 流水账 | ❌ 排除 |
| `memory/main.sqlite` | 471KB | **真记忆** | ✅ 同步 |
| `memories/MEMORY.md` + `USER.md` | **KB 级** | **真记忆** | ✅ 同步 |

> **规律：所有框架的本地库都分两种——「记忆库」（KB~MB，该同步）和「流水账库」（MB~GB，排除）。**
>
> **真记忆的体量，不到总量 1%。文件大 ≠ 值钱。**

我搬了 1.34GB，其中真正有价值的是几十 KB。剩下那 1.34GB 不是资产，是**负资产**——它拖慢检索、污染上下文、让你误以为「我迁移成功了」。

### 教训

> 迁移前先回答一个问题：**这个东西是「我的 AI 记得我」，还是「我和 AI 说过的话」？** 前者是记忆，后者是日志。日志可以留在原地，甚至可以删掉。

---

## 三、坑 3：记忆是二进制，迁不动就是迁不动

这是最硬的一堵墙。

OpenClaw 的长期记忆在 `memory/main.sqlite` 里——**一张 sqlite 表**。
Hermes 的长期记忆在 `MEMORY.md` / `USER.md` 里——**两个 markdown 文件**。

一边是结构化查询，一边是纯文本注入。**没有官方导出通道。**

我当时的选项只有三个：

1. 写脚本读 sqlite → 拼成 markdown（能做，但字段语义会丢：category、tags、重要性权重全没了）
2. 手动抄（我做了一部分，抄了两小时，抄到第 40 条就放弃）
3. 就让它烂在那儿

我选了 1 + 2 的混合，结果是**两边记忆都变得不完整**：新环境丢了分类信息，旧环境成了孤儿数据。

### 教训

> **跨框架迁移的真正瓶颈从来不是「怎么导出」，是「导出之后语义还在不在」。**
>
> 一个 memory 记录不只是那段文字——它是「文字 + 分类 + 标签 + 来源 + 时间」。压成纯文本那一刻，你已经损失了让 AI 判断「这条该不该现在想起来」的全部元信息。

顺便说一句，我在这件事上是有前科的：Bear、印象笔记，我都试过用它们给自己搭知识库，**全都死于同一个循环——搭系统的时候很有乐趣，需求一消退就停止维护，最后熵增获胜。** 手抄迁移，本质上就是同一个陷阱换了个壳。

## 四、坑 4：同名文件，不同格式

`cron/jobs.json` 在两边都存在。

同名，所以我很自然地直接覆盖了过去。然后定时任务全挂了——**JSON 结构完全不兼容**，字段名、嵌套层级、调度表达式，没有一处对得上。

同样的坑还有：

| 文件 | 冲突点 |
|------|--------|
| `cron/jobs.json` | 同名不同结构 |
| `openclaw.json`（46KB）→ `config.yaml` | 格式不同（JSON → YAML），且含大量框架特有字段 |
| MCP 配置 | 两边都叫 `mcp`，一边是 stdio 命令数组，一边是 server 对象 |

### 教训

> **「文件名相同」是迁移里最危险的信号。** 它让你跳过校验，直接覆盖。迁移清单里，每一个同名文件都必须当成「陌生格式」处理，先 diff 结构再决定。

## 五、坑 5：迁移完没有「验证」，只有「感觉」

搬完那天我心情很好。三天后才发现：有几个技能根本没生效，某个 MCP server 静默失败了。

**因为我没有任何验证手段。** 我当时的判断标准是「文件都在」。

后来我给自己定了三条硬验证：

1. **每条迁移过去的记忆，能独立取出来**（不是「文件存在」，是「查询得到」）
2. **每个技能能被真实触发一次**（不是「目录在」，是「跑通了」）
3. **迁移前后做一次行为对比**（问同一个问题，看回答里有没有那些只有它才知道的细节）

### 教训

> **「文件已拷贝」不等于「状态已迁移」。** 中间隔着一整个「加载 / 解析 / 生效」的链路，任何一环断了，你得到的都是安静的失败——没有报错，只有变笨。

## 六、坑 6：重复同步，制造重复数据

这是个 ID 幂等性问题，我踩得很实在。

我前两次同步，因为没有记录「本地这条内容对应云端哪一条」，结果**同一份记忆被推了两遍**，成了两条。第三次推的时候更糟：三方版本冲突，系统不知道该以谁为准。

关键概念是 **`base_version`**：每次推送必须带上「本地这条是基于云端哪个版本改的」，这样系统才能判断这是「新增」还是「改坏」。

- 写死 `base_version: 0` → 每次都当新增，永远冲突
- 必须用**云端当前返回的 version** → 三方合并才成立

配套的还有一张本地映射表（我这边是 `state.json`），记录「内容 hash → cloud_id / version」。**没有这张表，同步就是不可幂等的——你说十次「同步」，就得到十份数据。**

### 教训

> **同步 ≠ 拷贝。** 拷贝是一次性动作，同步是**有状态的持续过程**，必须有版本和幂等映射兜底。

---

## 七、坑 7：把「同步」当成「备份」

这是最大的一个认知坑，也是我复盘到最后一层才想明白的。

备份是**照片**——记录你某个瞬间的样子。
同步是**活人**——你搬家它自己跟过来，你两个设备各改一半它自动合并，你被改坏三天后它告诉你「回滚到周二吧」。

我最初的目标写的是「备份 + 迁移」。但如果只是备份，我得到的永远是一个**离线的、会过期的、需要我手动搬运的快照**。而我的 AI 每天都在变——今天教了它一个新流程，明天改了一个 Persona。备份到网盘的那一刻，它就开始腐烂了。

真正需要的是**账号**。

想想手机为什么从来不需要你「迁移通讯录」：因为你的联系人挂在 Apple ID / 账号上，换机只是重新登录。**AI 世界缺的从来不是「更好的记忆」，是这层账号体系。**

| | 记忆层（mem0 / Zep / Letta） | 在线同步层（账号） |
|---|---|---|
| 解决 | Agent 运行时**记不记得住** | 你教它的成果**跟不跟得走** |
| 单位 | 应用内的一条记忆 | 你的一个账号 |
| 换框架 | 归零 | 重新登录 |
| 类比 | 给助理配更好的笔记本 | 让所有助理共享你的员工档案 |

记忆是应用的，**账号才是你的**。

## 八、我最后是怎么做的（以及你应该怎么开始）

**结论先给：不要做「迁移」，要做「接入」。**

我把方案从「把 OpenClaw 的东西搬到 Hermes」换成「把两边接进同一个账号」，流程变成这样：

1. **先清点，后搬运。** 168 个角色 → 真实在用的 6 个；1.34GB 数据库 → 几十 KB 真记忆。**清点的产出是「删掉什么」，不是「搬走什么」。**
2. **映射语义，不映射文件。** 统一成 4 类对象：记忆（memories）、人格（personas）、项目（projects）、身份档案（profiles）。框架特有的东西留在框架里，不硬塞。
3. **用同步 API 而不是文件拷贝。** 推送 / 全量拉取 / 冲突解决三个动作，加一张幂等映射表。
4. **必须能验证。** 每条记忆可独立取出，每个技能真实触发一次。
5. **留一条回滚路。** 版本化的意义不是「存档」，是「改坏了能反悔」——我的 AI 人格文件曾经被静默覆写，三天后才发现，这种无声事故只能靠快照 + 回滚兜住。

具体到操作，两边各自要同步什么，我的清单是：

| 类别 | 同步 | 不同步 |
|------|------|--------|
| 记忆 | `MEMORY.md` / `USER.md` / 真记忆库 | 对话流水账（`state.db` / `memos.db`） |
| 人格 | 在用的人设 / Persona / system prompt | 收藏夹里的 162 个没用过的角色 |
| 技能 | 真实触发过的 Skills | 装了没跑的 |
| 配置 | MCP server 定义、模型偏好 | 框架特有字段、密钥（走环境变量） |

## 九、给正要换框架的你

如果你正准备从 A 框架换到 B 框架，我的建议只有三条：

1. **别打包整个目录。** 你会把 99% 的垃圾和 1% 的资产一起搬走，而且分不清哪个是哪个。
2. **先问「这是记忆还是日志」。** 这一句话就能砍掉 90% 的数据量。
3. **把迁移当成「接入一个账号」，不是「拷贝一次文件」。** 前者一次性、可复用、有版本；后者一次性、会腐烂、无法验证。

跨框架迁移这件事，行业里最普遍的现状是——**同一个灵魂被维护成了 N 份，然后慢慢分叉。** OpenAI 官方仓库里 `AGENTS.md` 和 `CLAUDE.md` 内容逐字相同（连内部引用都没改）；有人的项目里同时躺着 `.clinerules`、`.claude`、`.codex`、`.agents` 五个目录。

真正的问题从来不是「有没有灵魂文件」，是**「谁是你的唯一真相源」**。

我给自己的答案是：**账号。**
