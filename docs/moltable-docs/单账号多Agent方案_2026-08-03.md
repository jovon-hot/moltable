# Moltable 单账号多 Agent 支持方案

> 版本: v1.0 · 日期: 2026-08-03 · 状态: 待评审
> 关联: `开发与测试计划_2026-08-02.md`（Sprint 1 同步码方案 · 本方案为其升级版）
> 参考模式: GitHub Personal Access Token（一账号多 Token，每个有名字+权限）、
> mem0 `init --agent --agent-caller claude-code`、1Password 设备授权

---

## 1. 现状与问题

| 现状 | 问题 |
|------|------|
| 所有 Agent 共享账号级 `molt_xxx` API Key | 后端只能解析出 `user_id`，不知道是 Hermes / Claude / Cursor 谁在调用 |
| `api_keys` 表已有 `name` 字段，但无 Agent 概念 | 无法做 Agent 级用量统计、异常检测、设备管理 |
| 同步码（Sprint 1 计划 `molt_sync_xxx`）返回账号级 key | 换电脑找回的是「整个账号」而不是「某个 Agent」；一次性码换长期账号钥匙，风险大 |
| `did_registry` 表已存在（DID 天然是 Agent 身份） | 依赖 issuer/VC 签发链，MVP 过重；且与 API Key 认证体系未打通 |

**用户期望**：一个账号下多个 Agent（「我的 Hermes」「我的 Claude」「办公室 Mac 的 Cursor」），
每个 Agent 有独立身份标识、设备信息、在线状态；共享同一套记忆和 Persona；
可查看、命名、吊销某个 Agent；新 Agent 通过同步码/设备授权加入，无需重新注册。

---

## 2. 设计目标与核心决策

### D1 — Agent 是第一公民实体，不是 API Key 的别名

```
users (1) ──< agents (N) ──< api_keys (N)
  账号        身份+设备+状态      凭证（可轮换）
```

- `agents` 表 = 身份 + 设备信息 + 在线状态
- `api_keys.agent_id` = 凭证绑定：一个 Agent 可有 1..N 个 key（轮换/多设备），一个 key 只属于一个 Agent
- 记忆/Persona/项目保持 `user_id` 作用域不变 —— **所有 Agent 天然共享**（满足用户期望）

### D2 — API Key = Agent 的长期凭证（GitHub PAT 模式）

不引入新 token 类型。`molt_xxx` 仍是 API Key，但认证时同时解析出 `user_id + agent_id`。

| 备选方案 | 结论 |
|---------|------|
| **API Key 绑定 agent_id（本方案）** | ✅ 零破坏、可吊销、天然支持轮换、心智与 GitHub PAT 一致 |
| 单独 `agnt_` token 类型 | 新认证链路 + 客户端改动，收益低，P2 再议 |
| 额外 `X-Agent-ID` header 标识 Agent | ❌ 可伪造，Key 被分享后无法溯源，否决 |

### D3 — 同步码 = 设备授权加入（1Password 模式），不再返回账号级 key

Sprint 1 原方案 `POST /api/auth/sync` 返回账号级 `api_key`。本方案升级：

- 同步码（`molt_sync_xxx`）是**邀请函**，不是账号钥匙
- 消费时携带 `platform + device_info + agent_name`，服务端**创建 agents 行 + 签发 Agent 专属 key**
- 端点形状兼容 Sprint 1（`GET /api/auth/sync-code` + `POST /api/auth/sync`），响应多出 `agent_id`

### D4 — 在线状态 = 认证即心跳 + MCP ping

- 每次认证成功更新 `agents.last_seen_at`（复用 `get_user()` 已有的 last_active 更新路径）
- MCP `ping` 更新 `heartbeat_at`（轻量，不落审计）
- 前端判定：`last_seen < 5min` 在线（绿）/ `< 24h` 最近活跃（黄）/ `> 24h` 离线（灰）/ `revoked` 已吊销（红）

### D5 — Agent 级遥测走 `agent_events` 时间线

- 事件：`auth_success / auth_fail / tool_call / key_created / revoked`
- 用量统计：tool_call 计数 + 按 `memories.agent_id` 聚合
- 异常检测：新 IP 登录、高频 auth_fail → 对接现有 alerting

### D6 — 记忆溯源不做隔离

- `memories.agent_id` 仅用于**溯源**（哪条记忆是哪个 Agent 写的），不做数据隔离
- 未来 Pro 功能：按 agent 过滤记忆（`source = agent_id`）

### D7 — DID+VC 休眠，`agents` 表接管运营层

- `did_registry` 保留不删（已部署、有 RLS）
- `agents.did` 可空列 = 未来桥接 DID；启用时 `agents.did → did_registry.did`（见 §6）

## 3. 数据库 Schema（DDL）

> 在 Supabase SQL Editor 执行。SQLite 适配器需同步 `schema_sqlite.sql`。

```sql
-- ═══════════════════════════════════════════════════════════
-- 1. agents 表 — 核心：Agent 注册表
-- ═══════════════════════════════════════════════════════════
create table agents (
    id            uuid primary key default gen_random_uuid(),
    user_id       uuid not null references users(id) on delete cascade,
    did           text,                            -- 未来 DID 桥接（MVP 为 NULL）
    name          text not null,                   -- 显示名：「我的 Hermes」「办公室 Mac 的 Cursor」
    platform      text not null default 'unknown', -- hermes | claude | cursor | chatgpt | generic | unknown
    agent_caller  text,                            -- 调用方细分（mem0 --agent-caller 风格）: claude-code, hermes-agent, cursor-agent
    status        text not null default 'active',  -- active | suspended | revoked
    device_info   jsonb not null default '{}',     -- {os, os_version, hostname, arch, app_version}
    last_seen_at  timestamptz,                     -- 最近一次认证成功时间
    last_ip       text,                            -- 最近来源 IP（异常检测）
    heartbeat_at  timestamptz,                     -- MCP ping 心跳
    created_at    timestamptz not null default now(),
    revoked_at    timestamptz,
    updated_at    timestamptz not null default now()
);
create index agents_user_idx on agents (user_id);
create index agents_user_status_idx on agents (user_id, status);
create index agents_did_idx on agents (did) where did is not null;

-- ═══════════════════════════════════════════════════════════
-- 2. api_keys 改造 — 凭证绑定 Agent
-- ═══════════════════════════════════════════════════════════
alter table api_keys add column if not exists agent_id uuid references agents(id) on delete set null;
create index if not exists api_keys_agent_idx on api_keys (agent_id);

-- 兼容说明：agent_id IS NULL 的 key 视为「账号级遗留 key」，迁移时归入默认 Agent

-- ═══════════════════════════════════════════════════════════
-- 3. agent_invites — 同步码 / 设备授权
--    （取代 Sprint 1 计划的 admin_users.sync_code 账号级方案）
-- ═══════════════════════════════════════════════════════════
create table agent_invites (
    id            uuid primary key default gen_random_uuid(),
    user_id       uuid not null references users(id) on delete cascade,
    code_hash     text not null,                   -- PBKDF2(molt_sync_xxx) — 同 hash_api_key()
    code_prefix   text not null,                   -- 前 12 位用于展示
    agent_name    text,                            -- 预填名称
    platform      text,                            -- 预填平台
    status        text not null default 'pending', -- pending | used | revoked | expired
    used_by_agent uuid references agents(id),      -- 消费方
    used_at       timestamptz,
    expires_at    timestamptz not null default (now() + interval '7 days'),
    created_at    timestamptz not null default now(),
    revoked_at    timestamptz
);
create index agent_invites_user_status_idx on agent_invites (user_id, status);
create index agent_invites_code_hash_idx on agent_invites (code_hash);

-- ═══════════════════════════════════════════════════════════
-- 4. agent_events — Agent 生命周期 / 遥测时间线
-- ═══════════════════════════════════════════════════════════
create table agent_events (
    id          bigint generated always as identity primary key,
    agent_id    uuid not null references agents(id) on delete cascade,
    user_id     uuid not null references users(id) on delete cascade,
    event_type  text not null,   -- auth_success | auth_fail | tool_call | heartbeat | key_created | revoked
    tool        text,            -- tool_call 时的 MCP 工具名
    key_id      uuid,            -- 关联 api_keys.id
    details     jsonb not null default '{}',
    ip_address  text,
    created_at  timestamptz not null default now()
);
create index agent_events_agent_time_idx on agent_events (agent_id, created_at desc);
create index agent_events_user_time_idx on agent_events (user_id, created_at desc);

-- ═══════════════════════════════════════════════════════════
-- 5. memories 溯源（与 MCP save_memory 配合）
-- ═══════════════════════════════════════════════════════════
alter table memories add column if not exists agent_id uuid references agents(id) on delete set null;
create index if not exists memories_agent_idx on memories (agent_id) where agent_id is not null;

-- ═══════════════════════════════════════════════════════════
-- 6. did_registry — 休眠保留，不新建（见 §6）
-- ═══════════════════════════════════════════════════════════
```

**SQLite 同步**（`schema_sqlite.sql`）：`agents` 表同样定义；`api_keys`/`memories` 加 `agent_id` 列；
`agent_invites`、`agent_events` 建表。⚠️ 老 SQLite 库不会自动迁移新列 —— 删 `moltable_dev.db` 后重启。

## 4. API 设计

### 4.1 认证改造：`get_user()` → `get_auth_context()`

当前 `get_user()` 返回 `str user_id`。新增依赖 `get_auth_context()` 返回完整上下文，`get_user()` 保留为包装（不破坏现有 14 个调用点）：

```python
class AuthContext:
    user_id: str
    agent_id: Optional[str]     # API Key 绑定的 Agent（session/JWT 为 None）
    key_id: Optional[str]
    auth_method: str            # 'jwt' | 'session' | 'api_key'
```

**API Key 认证链（含吊销即时生效）**：

```
1. hash_api_key(key) → api_keys 查询
2. key 有效？  （is_active=True + expires_at 未过期 —— 顺带修复历史遗留的 expires_at 未检查问题）
3. agent_id → agents 查询 → status == 'active'？  否则 403 "Agent 已吊销"
4. 更新 agents.last_seen_at + last_ip（best-effort）
5. 落 agent_events（auth_success，采样）
```

### 4.2 端点清单

```
── Agent 管理（需用户登录：JWT / 账号级 key）─────────────────────
POST   /api/agents
       {name, platform?, agent_caller?}
       → 201 {agent: {...}, key: "molt_xxx", note: "仅显示一次"}
       配额: check_quota(user_id, "agents", ...) → 402

GET    /api/agents
       → {agents: [{id, name, platform, agent_caller, status, device_info,
                    last_seen_at, heartbeat_at, online, key_count,
                    key_prefixes: [...], memory_count, created_at}]}
       online 由服务端按 D4 规则计算

PATCH  /api/agents/{agent_id}
       {name?, platform?, agent_caller?}   → 重命名 / 改平台

DELETE /api/agents/{agent_id}
       → 软吊销: agents.status='revoked' + 级联吊销其所有 key(is_active=False)
       即时生效（每次请求查 status，无缓存）

POST   /api/agents/{agent_id}/keys        → 轮换密钥 → {key: "molt_xxx"}
GET    /api/agents/{agent_id}/events?type=&limit=50   → 遥测时间线
GET    /api/agents/{agent_id}/usage
       → {tool_calls_today, memories_written, last_active_at, ip_changes}

── 同步码 / 设备授权 ───────────────────────────────────────────
GET    /api/auth/sync-code?agent_name=&platform=
       → {sync_code: "molt_sync_xxx", expires_at}
       行为: 生成新码 → 旧码立即作废（与 Sprint 1 一致）

POST   /api/auth/sync                    # 无认证 — 新 Agent 首次接入
       {sync_code, platform?, agent_name?, agent_caller?, device_info?}
       → 201 {agent_id, name, key: "molt_xxx", profile: {user 摘要}}
       行为: 校验 code(pending+未过期) → 创建 agents 行 → 签发
             agent-bound key → code 标记 used(used_by_agent)
       ⚠️ 关键区别 (vs Sprint 1): 返回 Agent 凭证，不是账号钥匙

── Agent 侧（Agent 凭证认证）────────────────────────────────────
POST   /mcp ...                          # X-API-Key: molt_xxx → 自动带出 agent_id
POST   /api/agents/heartbeat             # X-API-Key → 更新 heartbeat_at
```

### 4.3 错误码

| 码 | 场景 |
|----|------|
| 401 | Key 无效 / 过期 |
| 403 | Agent 已吊销（key 有效但 agent revoked/suspended） |
| 402 | 超出 Agent 配额（升级提示） |
| 404 | Agent 不存在 / 非本人 |
| 409 | 同步码已使用 / 已吊销（幂等防重放） |

### 4.4 MCP 层影响

- `_resolve_api_key()` / `get_user()` 解析结果附带 `agent_id`，`auto_provision` 响应可加 `agent` 字段（Agent 知道自己是谁）
- `save_memory` 的 `source`：MCP 路径优先用 `agent.platform` 兜底；Sprint 1 的 `X-Agent-Platform` header 仍保留（非 MCP 路径有用）
- 新 Agent 接入后 `auto_provision()` 自动恢复记忆/Persona —— 流程不变，零客户端改动

## 5. 认证流程（三种接入路径）

```
路径 A — Dashboard 手动创建（GitHub PAT 心智）
  User ──POST /api/agents──▶ 得到 {agent, key}
  User ──把 key 配进 Hermes/Claude/Cursor MCP 配置──▶ 完成
  （一个账号可创建 N 个 Agent，每个独立 key，可单独吊销）

路径 B — 同步码加入（换电脑 / 新设备 / 办公室新机器）★ 主路径
  User    ──GET /api/auth/sync-code──▶ molt_sync_xxx（复制）
  User    ──粘贴给新 Agent（如发给「办公室 Mac 的 Cursor」）──▶
  Agent   ──POST /api/auth/sync {sync_code, device_info}──▶
            创建 agents 行 + 签发 Agent 专属 key（一次性码作废）
  Agent   ──配置 MCP → auto_provision──▶ 恢复全部记忆/Persona/项目
  User    ──Dashboard /dashboard/agents──▶ 看到新 Agent，可重命名/吊销

路径 C — 现有用户迁移（首次部署自动执行）
  对每个 agent_id IS NULL 的 api_keys 行：
    创建「默认 Agent」→ 绑定全部遗留 key
  → 用户可在 Dashboard 重命名为「我的 Hermes」，或为各设备拆分成独立 Agent
```

**同步码消费示例**：

```bash
# 用户生成
curl -s $API/api/auth/sync-code -H "X-API-Key: $ACCOUNT_KEY"
# → {"sync_code": "molt_sync_k8m2p4x9...", "expires_at": "..."}

# 新 Agent 加入（无任何凭证）
curl -s -X POST $API/api/auth/sync -H "Content-Type: application/json" -d '{
  "sync_code": "molt_sync_k8m2p4x9...",
  "platform": "cursor",
  "agent_name": "办公室 Mac 的 Cursor",
  "device_info": {"os": "macos", "hostname": "office-mac", "app_version": "1.2.0"}
}'
# → 201 {"agent_id": "...", "name": "办公室 Mac 的 Cursor",
#        "key": "molt_xxx", "profile": {"name": "...", "email": "..."}}
```

## 6. 与 DID+VC 方案的关系

| 维度 | did_registry（现有，休眠） | agents（本方案，运营层） |
|------|---------------------------|--------------------------|
| 主键 | DID 字符串 `did:web:...` | UUID |
| 身份证明 | 公钥 + VC 签发链 | API Key 绑定（PBKDF2） |
| 认证 | X-Agent-VP 验证 | X-API-Key → agent_id |
| 设备/在线 | 仅 last_seen_at | device_info + heartbeat + last_ip + events |
| 面向 | 未来去中心化 / 跨平台互信 | MVP 立即落地 |

**桥接路径（未来启用 DID 时）**：

1. `agents.did` 列已预留（可空）
2. 启用时：为每个 active agent 走现有 `enroll` 流程签发 DID，回填 `agents.did`
3. `get_auth_context()` 的 agent 分支优先用 `agents.did` 关联 `did_registry` 校验吊销状态
4. 现有 `/api/agents/enroll|renew|relocate` 端点保留，可作为「DID 优先」的替代接入路径，与 API Key 路径并存

> 决策依据（5 专家评审结论）：DID+VC 是包袱不是武器，用户不在乎协议名。
> MVP 用简单方案；DID 层作为未来能力储备，schema 留位不实现。

### 8.4 交互细节

- **重命名**：行内编辑（PATCH /api/agents/{id}）
- **轮换密钥**：确认弹窗 → 展示新 key（旧 key 立即失效）
- **吊销**：确认弹窗（红色，警示"该 Agent 将立即无法访问记忆"）→ DELETE
- **事件面板**：行内展开抽屉，渲染 `agent_events` 时间线（时间 + 事件类型 + IP + 工具名）
- **用量面板**：今日 tool_calls、记忆写入数、IP 变化次数（`GET /api/agents/{id}/usage`）
- Settings 页现有 api-keys Tab 保留（账号级脚本 key），文案区分「账号密钥」vs「Agent 密钥」

## 9. 安全考量

| 项 | 措施 |
|----|------|
| 同步码存储 | PBKDF2-HMAC-SHA256（复用 `hash_api_key()`），不存明文 |
| 同步码生命周期 | 一次性 + 7 天过期 + 生成新码即作废旧码 + 可手动吊销；消费返回 409 防重放 |
| 吊销即时生效 | 每次请求实时查 `agents.status`，无缓存；吊销 Agent 级联吊销其全部 key |
| 审计 | `agent_events` 记录 auth_success/auth_fail/tool_call；`audit_logs` 关联 key_id → agent |
| 异常检测规则 | 同一 agent 新 IP 首登 + 短时高频 auth_fail → 告警（对接现有 alerting） |
| 速率限制 | sync 10/min/IP · agents 创建 20/hour/user · 沿用 slowapi limiter |
| 历史遗留修复 | API Key `expires_at` 现在真正检查；吊销状态（is_active）与 agent status 双重校验 |
| Key 泄露溯源 | 每把 key 唯一绑定 agent + 独立 last_used_at —— 泄露后吊销该 agent 即可，不影响其他 |
